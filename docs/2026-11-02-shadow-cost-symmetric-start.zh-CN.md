# S1 在对称起点上的影子开销：来源与改法

日期：2026-11-02。状态：**Claude 分析与提案，待用户决定**；本文不改代码、不改验收标准。

依据：`state.md` §4.27（R2″，现行规则）、§4.31（G2 S1）、§4.32（G1 S1）；影子设计 `docs/2026-10-26-near-duplicate-shadow-design.zh-CN.md`；S1 分析 `docs/2026-11-01-shadow-slot-analysis.zh-CN.md`；代码 `src/sroqm/beam.py:414`–`:506`（影子推进、判定、准入）。

## 1. 结论

S1 下对称起点的影子开销（占 SCF 周期 14–18%，现行规则 7–10%）**93% 来自加密窗口（densify）里登记的影子，而这些影子在两种规则下一次都没被准入过**。原因：加密窗口的每一步都做完整搜索（加 40 个随机取向），beam 满员，近重复晋升出来时能量都在 3 条 lineage 之上，准入前就因为没有位置被丢掉。traj2（G2）不会进入加密窗口，所以**只在加密窗口里不登记影子**（D1）能去掉 G1 上几乎全部的影子开销，而不碰 G2 的路径。

## 2. 证据

脚本 `benchmarks/out/analyze_shadow_cost_20261102.py`（只读 `rows.jsonl`；`--kind` 按登记那一步的搜索原因分组，`--admissible` 按登记时能否进 beam 分组）。

**按登记那一步的搜索原因分组**（影子周期占比 = 该组影子 SCF 周期 / 全部影子 SCF 周期）：

| 批次 | densify | escalate | start | no-search / periodic / lost | 准入（spawn / revive）来自 |
|---|---|---|---|---|---|
| G1 S1（§4.32，4 条） | 529 个，**93%**，准入 0 | 20 个，4% | 8 个，1% | 36 个，2% | 无 |
| G1 现行规则（R2″ s0–s3） | 248 个，**88%**，准入 0 | 13 个，4% | 9 个，6% | 25 个，2% | escalate 1 次 revive |
| G2 S1（§4.31） | 0 | 53 个，50% | 25 个，20% | 38 个，30% | escalate、start、periodic、no-search |
| G2 现行规则（§4.29） | 0 | 55 个，49% | 17 个，15% | 43 个，36% | 同上 |

- G1 S1 全部 449 个晋升（`distinct` 427、`separated` 22）在晋升那一刻都比满员 beam 的 3 条 lineage 能量高，准入前因"full"被丢弃（`beam.py` 准入循环里 `admission_slot` 为 full 时直接跳过，不写影子 log，所以 log 里看不到准入记录）。
- 加密窗口里，影子登记后多数只跟 1 步就晋升或判同态；下一步的完整搜索又会重新登记新的一批。
- 整体：G1 S1 影子周期 10436 / 66324（15.7%），其中 densify 9731。

## 3. 改法

| 编号 | 做法 | G1 上的效果（按上表估算） | 对 G2 的影响 | 风险 |
|---|---|---|---|---|
| **D1（建议）** | 搜索原因为 densify 的步，不从搜索去重 / 准入登记新影子（已有影子照常推进） | 影子周期 10436 → 约 700，占比 15.7% → 约 1.2% | 无：traj2 不进加密窗口，G2 两批 densify 登记都是 0 | 对称起点附近若有像 B / B′ 那样会分开的近重复，在加密窗口里不会被跟踪；但加密窗口每步都重新做完整搜索，窗口结束后还有定期 / 升级搜索。G1 两种规则下 densify 影子准入都是 0 次 |
| D2 | 登记时 beam 满员且近重复比所有 lineage 都高，就不登记 | 约省 93%（与 D1 相近） | **有**：G2 两批里各有 1–2 次这类影子后来被 spawn / revive（lineage 丢失或被替换后腾出位置），这些准入对结果有没有影响没查 | 依赖登记时的能量排序，之后能量会变 |
| D3 | 不改（接受 G1 上约 14–18% 的影子开销） | — | — | 只是成本，结果 4 / 4 |

**建议 D1**：G2 的行为完全不变（不需要重跑 G2），只影响已经知道没用的那部分影子；实现只是在登记处加一个条件。

## 4. 验证（D1 实现后）

- G1 复核 × 4（对称起点 11 步，S1 + D1）：应 4 / 4 通过，影子周期占比降到约 1–2%，墙钟比 §4.32 少约 1/7。
- G2 不重跑：D1 的条件在 traj2 上从不成立（两批 densify 登记均为 0），可用一次 traj2 前几步的冒烟确认影子 log 与 S1 一致。

## 5. 验证结果（2026-11-02，183，`state.md` §4.33）

用户原话（2026-11-02）："可以"（按 D1 实现并交 G1 复核 × 4）。实现为开关 `BeamParams.shadow_skip_densify`（默认 False），`bench_beam.py --shadow-skip-densify`。

| | G1 S1（§4.32） | G1 S1 + D1 |
|---|---|---|
| 结果 | 4 / 4 | 4 / 4 |
| 登记影子（4 条） | 593 | 139 |
| 影子周期 / 占比 | 10436 / 15.7% | 2148 / 3.2% |
| 全部周期 | 66324 | 66892 |
| 每条用时 | 2.32–3.01 h（12 核，PBS） | 2.30–3.22 h（10 核，183） |

- 影子开销按预期下降（第 3 节估约 1.2%，实测 3.2%：多出的部分来自 escalate、lost 等非 densify 步，这一批升级搜索较多）。
- **总周期没有下降**：非影子周期多了约 8900，与批间随机波动（升级搜索次数）相当，所以这一批看不出墙钟收益；要量化 D1 的墙钟收益，需要同一输入的确定性对照或更多批次。
- 加密窗口内搜索原因为 `lost` 的步（s3 第 1 步）不在 D1 范围内，登记 36 个、0 次准入。

- D1 的节省是按本批数据估算，没跑过。
