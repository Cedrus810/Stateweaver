## 2. 优先问题

### P1：同态近似同时控制删候选与验收，存在检查盲区

位置：`src/sroqm/search.py:112–117`、`src/sroqm/beam.py:327–331,354–369`、`benchmarks/bench_beam.py:49–65`。

- `judge_step()` 在 σ≥0.9 时直接判 `same-state`；`is_warn()` 只检查 `energy` 分支，因此该分支没有能量偏差的兜底检查。现有 `tests/test_bench_beam.py:23–26` 还明确要求“同态时不论能量都通过”，这是当前合同，不是漏写了一个条件就能直接改掉的细节。
- R2 t2 第 5 步 lineage 1 的 σ_ref=0.9080504、ΔE_ref=+0.2007378 mHa。它符合当前同态阈值，却有显著高于已有收敛噪声的能量差。**这条 lineage 当时没有被选中，所以本轮没有观察到它导致的假通过；它证明单独通过该同态判据不足以保证能量一致。**
- t2 第 0 步 B 是否被 B′ 去重掉，仍是推断。标签、能量和后续轨迹不能补出缺失的当时候选帧与成对重叠，E6 也未复现 B′。

最小下一步：在搜索去重、准入前去重、准入后去重、merge 分别记录候选 ID、保留者、σ、同几何 ΔE、来源与决策，并保存窗口内候选帧。先分清“近似相似”“同一收敛解”“可省略后续搜索扩展”，再决定判据；本轮不提高阈值或改变验收。

### P1：完整搜索全未收敛时，会漏记已有 anchor 窗口内的 pending

位置：`src/sroqm/search.py:267–268` 对比 `274–276`；下游 `src/sroqm/beam.py:284–289,440–475`。

确定的控制流：有 ACTIVE 态并传入本几何有效 `anchor`，但本轮 scratch 和枚举均未收敛时，`level1` 为空，函数提前返回；返回值的 `pending=0`、`pending_frames=()`。此前 `enum` 中即使有保留且能量在 anchor 窗口内的 NC 候选，也不会经过 `_pending()`。

后果：beam 只记 `search_empty`，这些候选不进入续算队列；如果没有独立的 refresh unknown 或其他信号，它们也不会拉动刷新或升级。**这是静态可确认的遗漏路径；本轮 R2 没有出现 `n_states=0` 的搜索，不把它称为本次 WARN 的根因。**

最小修复：提前返回前用已知有效 anchor 分类并保留 NC；无 anchor 时应明确表示覆盖未解决，不能把无法分类等同于 pending 为零。后续回归应覆盖“ACTIVE 仍有效 + 搜索全 NC + 窗口内候选”的分支。

### P1：失败的 beam step 会留下已推进的内部状态

位置：`src/sroqm/engine.py:111–149`、`src/sroqm/beam.py:215–222,234–249,350–364,388–408,496`。

`Engine.finish()` 在发现、准入和最终力确认之前就 push 历史并增加 engine.step；beam 同时修改成员状态。之后搜索、fingerprint 或全部梯度计算失败会抛错；`finally` 释放 SCF 对象，却没有恢复成员历史、选择、调度器、pending 或 ID。beam.step 只在最后增加。

后果：调用方若在同一实例重试，可能处于“beam 步号未前进、成员历史已经前进”的状态。资源释放不等于事务回滚。当前没有证据表明 R2 发生过这种异常。

下一步合同：先暂存并验证结果，成功后统一提交；或先明确失败实例不可继续使用并阻止重试。checkpoint/restart 应建立在明确的提交边界上。

### P2：R2 的批作业成功状态不能代表子运行通过

位置：`benchmarks/out/perf_r2_yayoi12_20261023.zsh:49–56`；`benchmarks/bench_beam.py:214`。

四个回放后台启动后，脚本只执行无参数 `wait`，没有逐 PID 收集退出码，最后 `echo done` 决定脚本最终状态。t2 的 warn 按 CLI 合同应返回 1，但外层仍能正常写出 done、成功结束。`sroqm_r2.o18327` 确实以 done 收尾；判门必须读取 JSON，不能凭 PBS 完成状态。

最小修复：收集每个 PID 与退出码；分别记录执行是否完整、coverage 是否通过；核对输出存在且有预期 60 步，再生成机器可读汇总。环境激活等前置失败也应立即终止。本轮不改历史启动脚本。

## 3. 两个诊断结论需要收紧

**“被筛掉的候选都很高，因此筛选无关”还不足以排除因果。** `src/sroqm/search.py:184–195` 不仅淘汰候选，还把保留者的第二段 IMOM 参照改成短段结果帧。高 E_4 不能严格界定最终能量，也不能排除重设参照改变保留候选的收敛路径。因此 `state.md` §4.20 / §4.22 的“与筛选无关”应读作“现有被丢候选的短段能量没有提示直接漏掉低能候选”，尚非排除证明。

需要区分三个对照：连续完整求解；分段求解但全部保留；分段求解并淘汰。前两者识别分段 / 参照改变，后两者识别淘汰效应。保持输入、方法、资源与参考固定；本轮不启动这些实验。

**E4 是局部否定证据。** 单几何、8 个随机起点得到 8 个驻点，足以说明这里的有限枚举没有覆盖全部相关方向，不能据此证明 M1/M2 在所有几何都必然失败。1/8 也只是这个小样本的命中比例，不能直接当作跨几何固定概率来承诺 N 次搜索的漏率。

## 4. 成本与可复现性尚缺的证据

- `benchmarks/bench_beam.py:81–95` 只读取驱动进程 RSS。ProcessExecutor 把 SCF / mf 留在子进程，所以 R2 约 245–264 MiB 的 `peak_rss_mb` 不是整条运行的峰值内存，不能与旧串行 RSS 直接比较。
- `src/sroqm/executor.py:137–143` 的 worker 梯度与 fingerprint RPC 没有返回计时。`beam.py` 的物理 SCF 账本不包含这些独立 RPC 时间；整体步耗时包含它们，不能把账本内的 gradient=0 当作梯度没有成本。
- 结果顶层只有 `params/run/summary/rows`，未冻结源码 hash（含 dirty diff）、完整 MethodSpec/Tolerances、输入 / 参考 hash、CPU 与依赖版本。当前工作区存在性能相关未提交修改；HEAD 本身不能唯一代表运行源码。
- R1′ 40 核、R2 另一节点 12 核，与旧 10 核估计值不是同资源完整对照；R1 的约 6 h 还是中止后外推。现有数据支持已完成运行的墙钟数字，不支持把全部差异归为算法节省或声称 G3 已过。
- 未提供参考时 `benchmarks/bench_beam.py:118–122` 仍写 `passed=True`，汇总生成零 miss / warn；应独立记录 `evaluated=false`，避免消费结果的工具把未判定误读为验收通过。
- 文档发生漂移：README 仍写正式实现第 21–59 步未回放；搜索设计开头仍写筛选、并行未实现；Stateweaver 设计仍写 beam 没有全部 Frame 接口，而当前已有 `BeamResult.frames`。其中后者仍缺只读 / 提交快照保证，不能简单认定设计合同已满足。
- `BeamResult` 仍不能直接接 `run_nve()`：`md.py:45–46` 要求 `scf_iterations` 和 `status.value`，前者缺失、后者是字符串。多态固定路径回放不等于已交付多态 NVE 驱动。

## 5. 建议的处理顺序

1. 先补候选身份、成对去重证据和运行 manifest；修复空搜索漏记 pending、外层退出码汇总这两条确定路径。

3. 为分段参照改变与真正淘汰设计独立对照，再决定随机取向 / Newton 等发现增强。
4. 补失败步骤提交边界与执行器故障合同，随后重做固定协议的覆盖与成本验收；通过前继续标记 Phase 3b 未验收。
