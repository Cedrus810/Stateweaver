# Phase 3b 成本报告

日期：2026-10-29。用户原话（2026-10-29）："可以"，指同意写本报告。收口计划 Task 7 Step 2；验收报告 `docs/2026-10-29-phase3b-acceptance-report.zh-CN.md` §5。数据：`benchmarks/out/cost_report_20261029.py`（读各轮回放 JSON）、`state.md` §4.16–4.28。体系与方法全部是 [Fe(H₂O)₆]²⁺ / UKS-B3LYP / def2-SVP / DF，`conv_tol = 1e-7`。

## 1. 口径与限制

- **墙钟**：`bench_beam.py` 记录的每步 `beam.compute()` 时间（含推进、发现、准入、梯度），一条 run 的总和。
- **SCF 周期**：每步账本（`trace["tasks"]`）里所有物理 SCF 的周期数，按任务来源分类。
- **worker 秒 / 墙钟**：所有 SCF + 梯度计时之和除以墙钟，进程执行器下约等于"平均有几个 worker 在算"，串行下约等于 1。
- **不同轮次的硬件和执行方式不同**（下表注明），墙钟只能在同一行内比较；跨行比较以 SCF 周期为准。
- **内存只记了驱动进程的峰值**，进程执行器下 worker 的内存没有记录。
- 每组只有 4 条 run。

## 6. 仍在的成本

1. **SCF 周期本身**：DF 落盘修复后，DF / 格点重建只占每步时间的 1–3%（§4.16），其余几乎都是 SCF 迭代，只能靠少算（少搜、少周期）或多核并行。
2. **并行效率**：worker 秒 / 墙钟在 3 个 worker 时约 2.0、2 个 worker 时约 1.6–1.75、4 个 worker 时约 2.7–2.9。非搜索步只有 9–13 个任务、长短不一，worker 经常空等。
3. **升级搜索**：traj2 墙钟的约 1/3（第 4 节）。
4. **1a 随机采样**：对称起点周期的约 1/3，目前在加密窗口的每一步都采样，而漏态只出现在第 1 步（§4.18–4.24）。

## 未确认（Claude 推断）

以下是降低成本的可能方向，都没有做过实验，也都没有经用户确认：
- 升级搜索加冷却（例如两次升级之间至少隔若干步）或每条上限：按第 4 节，traj2 最多可省约 1/3 墙钟；风险是延迟找回漏态。
- 1a 只在加密窗口的第 1 步采样：按 R1″ 的数据（§4.24），第 2–4 步搜索本身都已找到最低态；对称起点约可省 1/4 周期。风险是第 2 步以后仍有漏态时没有兜底。
- 非搜索步把任务数少的批次合并、或减少 worker 数，以提高并行效率；收益未知。
